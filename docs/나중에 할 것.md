# 툴픽 v2 기능 단점과 개선안

2026-10-30 코드 리뷰 결과. 동작이 맞는지보다, 사용자와 운영자가 실제로 겪을 불편과 한계를 정리했다.
"큰 변경"은 AGENTS.md 3장 기준이다. 설계 문서를 쓰고 사람 승인을 받은 뒤에 구현한다.

## 높음: 사용자가 바로 느끼는 문제

### 1. 로그인이 자주 풀린다
- **원인**: 로그인 세션이 웹 서버 메모리에 있다. Render 무료 서버는 15분 동안 요청이 없으면 잠들고, 그때 프로세스가 내려가 세션이 전부 사라진다. 재배포할 때도 같다.
- **영향**: 잠깐 자리를 비웠다 오면 다시 로그인해야 한다. 북마크와 관리자 화면 이용이 불편하다.
- **개선**: (a) Spring Session JDBC로 세션을 DB에 저장한다(`V2__` 마이그레이션 필요, 큰 변경). (b) remember-me 쿠키를 둔다(보안 설정 변경, 큰 변경).

### 2. 첫 화면이 최대 1분 걸린다
- **원인**: Render가 잠든 뒤 첫 요청에서 깨어나는 데 약 1분이 걸리고, Neon DB도 5분 동안 쓰지 않으면 정지한다. 순위 화면은 Vercel 캐시가 가려 주지만, 로그인·북마크·관리자·MCP 요청은 캐시되지 않는다.
- **영향**: 처음 들어온 사용자나 MCP 클라이언트가 오래 기다리거나 시간 초과(60초)를 겪는다.
- **개선**: 잠들지 않는 호스팅으로 옮긴다. 또는 낮 시간에만 외부 cron으로 health를 호출해 깨워 둔다. 깨워 두는 방식은 무료 사용 시간과의 균형을 따져야 한다.

### 3. 프론트엔드 배포가 백엔드 상태에 따라 실패한다 (2026-10-30 실제 발생)
- **원인**: 헤더가 빌드 중에 분야 목록을 백엔드에서 받아 온다(`frontend/components/Header.tsx:20`). Render가 잠들어 있으면 페이지마다 60초를 넘겨 빌드가 실패한다.
- **영향**: `main`에 푸시해도 배포가 실패할 수 있다. 직전 성공 배포가 유지되므로 사이트가 내려가지는 않지만, 새 변경이 반영되지 않는다.
- **개선**: 빌드 중 요청에 짧은 시간 제한(예: 5초)을 두고, 실패하면 빈 목록으로 진행하게 한다. 수정은 한 곳이지만 화면 코드라 승인이 필요하다.

### 4. 새 순위가 화면에 늦게 보인다
- **원인**: 배치는 다른 프로세스라 웹 캐시를 비울 수 없다. 웹 순위 캐시 10분과 Vercel 캐시 1시간이 겹친다.
- **영향**: 배치가 끝난 뒤에도 최대 1시간 10분쯤 어제 순위가 보인다.
- **개선**: 배치가 끝날 때 Vercel on-demand revalidate(재검증 요청)를 호출한다. 웹 서버를 거치지 않아 단순하다.

### 5. 관리자가 승인해도 오늘 순위에 안 나온다 (v1과 같은 한계)
- **원인**: 순위 계산은 배치 안에서만 돈다. 관리자 승인 API는 상태만 바꾸고 순위를 다시 계산하지 않는다.
- **영향**: 검수 대기 레포를 승인해도 다음 날 배치까지 순위에 반영되지 않는다.
- **개선**: 승인 뒤 그날 순위를 다시 계산한다(DB만 쓰는 작업이라 원칙에 맞음). 순위 계산 변경이라 큰 변경이다.

## 중간: 데이터 품질과 범위의 한계

### 6. 90일 넘은 레포는 아무리 떠도 발견되지 않는다
- **원인**: 후보 검색 조건이 "생성 90일 이내, 스타 100 이상"이다.
- **영향**: 오래된 프로젝트가 갑자기 화제가 되어도 순위 후보에 들어오지 못한다.
- **개선**: 생성일 대신 "최근 푸시와 스타 수"로 검색하는 두 번째 쿼리를 추가한다. GitHub API 호출이 늘어 큰 변경이다.

### 7. 판별 순서가 "규모"를 보고 "성장"은 보지 못한다
- **원인**: 판별 순서가 최근 스타 수다. 스타 3,000개에서 정체된 레포가 스타 150개에서 하루 50개씩 느는 레포보다 먼저 판별된다.
- **개선**: 스냅샷이 2개 이상이면 하루 평균 증가량으로, 1개뿐이면 스타 수로 정렬하는 혼합 기준을 쓴다(판별 규칙 변경, 큰 변경).

### 8. 판별 대기열이 계속 쌓이는데 보이지 않는다
- **원인**: 발견은 하루 최대 300개, 판별은 100개라 차이가 계속 쌓인다. 60일이 지나면 판별 대상에서 조용히 빠진다.
- **영향**: 판별 기회를 영영 못 받는 레포가 생기는데, 얼마나 되는지 아무도 모른다.
- **개선**: 배치 로그에 "대기열 N개, 오늘 대상에서 빠진 수 M개"를 남긴다. 숫자를 보고 발견 상한(300)을 판별 상한에 맞춰 줄일지 정한다.

### 9. 규칙으로 거절된 레포를 되살릴 화면이 없다
- **원인**: 관리자 화면은 검수 대기(PENDING_REVIEW)만 보여 준다. 규칙으로 거절되면 판별·수집·순위에서 모두 빠진다.
- **영향**: 이름에 `awesome`이 들어간 진짜 도구가 걸리면 SQL을 직접 써야 되살릴 수 있다.
- **개선**: 관리자 화면에 "규칙 거절 목록" 탭을 추가하고 같은 승인 API를 다시 쓴다. 프론트엔드 변경이라 승인이 필요하다.

### 10. 수집에서 빠진 레포가 돌아오지 못한다
- **원인**: 공개되지 않았고 60일 넘게 푸시가 없는 레포는 수집이 멈춘다. 푸시 시각은 수집할 때만 갱신되므로, 다시 활동해도 알 방법이 없다.
- **개선**: 일주일에 한 번 빠진 레포 전체를 가볍게 수집한다. GraphQL 100개씩이라 비용이 작다.

## 운영: 문제가 생겨도 모르는 부분

### 11. 판별이 일부만 돼도 "성공"으로 끝난다
- **원인**: AI 한도 초과, 인증 오류, 마감 시각 도달은 의도적으로 성공(종료 코드 0)으로 처리한다.
- **영향**: 키가 만료돼 며칠째 판별이 0개여도 알림이 오지 않는다.
- **개선**: "판별 0개인데 대기열이 있음" 같은 경우는 경고 종료 코드나 알림으로 구분한다.

### 12. 배치 상태를 볼 화면이 없다
- **원인**: v1의 `/internal/jobs/{id}`를 없앴다. 지금은 Actions 로그나 DB를 직접 봐야 한다.
- **개선**: 관리자 전용 `GET /api/admin/batch-runs`로 최근 실행 기록을 보여 준다(읽기 전용).

### 13. 매일 배치가 외부 토큰 하나에 달려 있다
- **원인**: cron-job.org와 GitHub 토큰(만료 있음)에 기대고 있다. 토큰이 만료되면 배치가 멈춘다.
- **개선**: Actions `schedule`을 예비로 함께 켠다(늦더라도 돈다). 같은 날 중복 실행은 안전하게 처리된다. cron 실패 알림 메일도 반드시 받게 해 둔다.

### 14. 백업이 없다 (2026-10-30 결정 사항, 기록만)
- 시점 복구는 6시간뿐이고, 스타 기록은 다시 모을 수 없다.
